# 设计决策记录

> 记「为什么这么做」，不记「做了什么」（后者看 README）。每条给出：背景 → 决策 → 代价。
> 目的是让后来者（包括未来的自己）在改动前知道哪些是**有意为之**，而不是随手写的。

## D1. AI 只输出指令，绝不接触像素
- **背景：** 生成式编辑会重绘原图，细节（睫毛、砖缝、噪点纹理）在两张图之间漂移，
  "只把暗部提一点、其他一模一样"这种诉求做不到。
- **决策：** 模型只输出结构化 JSON 指令，由本地确定性算子执行；模型永不参与像素运算。
- **代价：** 表达能力受算子集合限制（目前 48 个）；要新效果必须新增算子，而不是"让模型画"。

## D2. 算子契约只有一个来源
- **决策：** `cogitator/ops.py` 的 `SPECS` 同时负责：参数校验、生成给模型看的手册、索引实现。
  新增算子必须同时被这三处看见，否则校验器会拒绝。
- **代价：** 加算子比"随手写个函数"麻烦；换来的是**不可能出现"手册里写了但执行不了/执行了但没校验"**。

## D3. 非破坏性管线 + 快照撤销（60 步）
- **决策：** 源图永不改写；一切改动是图层上的有序算子列表；撤销是弹出最后一批算子（快照式）。
- **代价：** 内存里要留 60 份文档快照（实测可接受）；换来做不到"部分撤销单条像素操作"也没关系——
  因为每步都是算子，随时可改参数重放。

## D4. 批量是原子的
- **决策：** 一批算子要么全部生效，要么全部不生效；一批只占**一次**撤销。
- **对比：** 有些同类工具（如 photocraft）是"每条命令各记一次历史、非原子事务"。本项目的
  语义更适合对话式修图：用户说"提亮并降色温"，失败时不应该只应用了提亮。

## D5. 原图对比的基准是"只含几何算子的渲染"
- **决策：** 对比基准不是原始文件，而是把裁切/旋转/校正应用后的画面。
- **为什么：** 否则裁切之后原图与成品画幅不同，叠加对比毫无意义。
- **代价：** 需要维护一条独立的渲染路径（`render_original()`），并有断言守住两者同画幅。

## D6. 预览按显示尺寸渲染，参数同比缩放
- **决策：** 预览最长边默认 1400px；以像素为单位的参数（锐化半径、暗角羽化等）按渲染比例缩放，
  使预览与"全分辨率渲染后缩小"在数值上等价。
- **代价：** 需要一套缩放映射与断言；换来预览能在 24MP 上做到秒级响应。
- **纪律：** 因此**绝不能**把"预览 100%"说成"输出像素 1:1"（界面文案与断言都在守这条）。

## D7. RAW：三条解码路径，解码只影响导入
- **决策：** `rawpy`（装了就用）→ Windows 系统 WIC → CR3 内嵌 JPEG 保底；结果落盘为普通图片。
- **为什么：** 解码差异若渗透到渲染层，会导致"同一工程在不同机器上出图不同"。落盘即隔离。
- **代价：** 导入时多写一份副本（占磁盘）；换来工程可移植、渲染确定。

## D8. 输出像素查看独立于缩放
- **决策：** 单独做「输出像素」模式（服务端按视口全分辨率渲染 + 按 rev 缓存），不与预览缩放混用。
- **代价：** 两种查看模式互斥；该模式下不做原图对比（基准尺寸不同）。换来真正的 1:1 判断能力。

## D9. 外部引擎走进程边界，默认关闭，不进管线
- **决策：** 通过命令行调用外部引擎（如 photocraft），产物以**新图层**回到工程；
  调用不写进图层算子列表，因此不影响可重放性；功能默认关闭，需显式启用。
- **代价：** 对话里的 AI 暂时不能自己发起（见 GAPS G1）；换来不破坏 D1/D3/D7 建立的可复现性，
  也不会因为外部项目处于早期而拖垮本项目。

## D10. 前端零构建，不引入外部依赖
- **决策：** 原生 HTML/CSS/JS，无打包器、无 CDN、无外链字体；静态资源带 `no-store`。
- **代价：** 不能享受框架生态；换来"双击即用、离线可用、改一行就生效"。
- **衍生纪律：** 让模型重写 CSS 时，必须先校验"覆盖旧版全部选择器 + 保留承载交互的硬规则"
  （`-webkit-user-drag:none`、`touch-action:none`、`.hidden !important`、`body.cmp-wipe`…），
  否则样式改动会静默破坏交互。

## D11. 界面不依赖浏览器原生对话框
- **背景：** Chrome 在多次弹窗后会静默阻止，`confirm()` 返回 false，按钮表现为"点了没反应"。
- **决策：** 一律用应用内 `<dialog>`；点击后立即给出反馈；`fetch` 全部包 try/catch。

## D12. 诚实标注优先于好看
- **决策：** 凡是能力边界都写在界面上与 README 里：预览 100% 不是输出像素、未装 rawpy 时 RAW 取内嵌
  预览（无高光宽容度）、RMBG-2.0 是非商业许可、外部引擎处于早期阶段。
- **代价：** 文案更长、卖点不夸张；换来用户不会因为误解而踩坑，也换来信任。

## D13. MCP 门面不引入第二份契约
- **决策：** `cogitator/mcp_server.py` 只做 stdio↔HTTP 桥，命令清单直接复用
  `/api/ops/manual` 里的结构化 `specs`；MCP 进程**不导入应用本体**（保证 stdout 只走协议）。
- **代价：** 需要应用已在运行；换来零重复契约、零协议污染风险。

## D14. 蒙版是「可见性」还是「作用域」——两者都要
- **背景：** 原实现里蒙版只决定图层可见性。于是"渐变蒙版"的效果是把画面擦成透明，
  而不是把调整限制在选区里——「只压天空」这类最常用的局部调整根本无法表达。
- **决策：** 蒙版算子新增 `scope` 开关。
  `scope: true` → 蒙版作为后续调色的作用域（调色算子按蒙版权重把结果混回原像素），不改可见性；
  缺省 `false` → 仍是原来的抠图语义。
- **为什么这样不会改坏旧行为：** 抠图场景下选区之外本来就透明，混合与不混合的**可见结果一致**；
  而 `scope` 缺省为 false，所有既有工程不受影响。
- **代价：** 调色算子现在要读当前蒙版（多一次广播乘加）；实测对 24MP 渲染时间无可感影响。
- **附带修掉的两个既有缺陷：**
  1. 蒙版步骤无法微调：`ops/update` 在把记录交给校验器前没摘掉 `mask_file`，
     导致任何蒙版步骤都报"不认识参数 mask_file"；
  2. `mask_brush` 的记录不含必填参数 `strokes`，于是这一步永远无法微调（校验说缺少 strokes）。
