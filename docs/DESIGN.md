## 交互细节（v1.4.6 ~ v1.4.7，依据 MiMo 的评审清单）

| 问题 | 现在的行为 |
| --- | --- |
| 抠图 10 秒、AI 对话几十秒，只有转圈看不出死活 | 加载层显示**已用时**（「模型思考中…已 12s」）；画布带 `aria-busy` |
| 长任务可被重复点击（连点两次发送会把状态叠乱） | 对话 / 撤销 / 重做入口加守卫，忙时提示「上一步还没完成」 |
| 等待期间对话区空白，用户以为没点上 | 立刻插入「已发出」占位气泡（省略号走动） |
| 失败时辛苦打的指令被丢掉 | **把输入内容还给用户**并就地显示失败原因，改一句即可重发 |
| 空状态只有一句「还没有打开图片」 | 主按钮「打开图片」+ **最近工程**列表（点击直接打开）+ 拖入文件时高亮落点 |
| **无法放大查看细节**（适应视图总是缩图） | 顶栏缩放循环：**适应窗口 → 预览 100% → 预览 200%**。⚠️ 预览是按显示尺寸渲染的下采样栅格（6000px 的照片预览只有约 1400px），所以「预览 100%」是按**预览像素**显示，观感≈把成片缩到该尺寸看——**判断不了输出像素级的锐化** |
| **真正按输出像素检查锐化** | 顶栏 **「输出像素」** 开关：服务端全分辨率渲染当前视口后裁切，1:1 呈现，**拖动即可平移**。24MP 实测首次渲染 2.7s，之后平移 0.01s（按 rev 缓存整幅渲染，平移只做裁剪+编码）。该模式下不做原图对比（基准尺寸不同），退出即回到预览 |
| 十几步的管线要滚很久才找得到开头 | **长管线折叠**：超过 8 步时默认显示「最新 6 步 + 最早 2 步」，中间折成一行，点开即展开；微调目标所在图层强制展开，避免滑杆失去落点 |
| 分不清某素材是否已用、用在哪 | **素材↔图层归属**：素材行标出「已用于 L1、L2」，点一下跳到对应图层；图层头显示来源素材标签（不再只是"已在图层中"） |
| 右侧面板写死 400px，窄窗口几乎不可用 | **左边缘可拖宽**（280~720px，记进本地存储）；窗口窄于 1040px 自动变为上下布局 |
| 快捷键没有发现性 | 顶栏 `?`（或按 `?`）打开**快捷键与用法**表；并补上 **Ctrl+Z / Ctrl+Y / Ctrl+S** |
| 每次导出都要重填质量与路径 | **导出参数记忆**（格式/质量/尺寸上限/目录），下次打开对话框自动回填 |

---

  <工程名>/document.json      编辑配方（管线步骤、图层、画布）
  <工程名>/chat.json          你与 AI 的对话记录
  <工程名>/exports/           成片
  <工程名>/sources-only-copy/ 仅当该源图在磁盘上找不到别的副本时才保留
  说明.md                     还原步骤 + 每个源图"可否重建"的逐条依据
```

判定依据不是猜的：工程的 `document.json` 里每个素材都记着 `original`（导入时的原图路径），
原图还在就说明源图可重建、删除无损失；**没有记录的（粘贴 / 拖入的图）才复制进存档**。
本次 15 个工程里共 12 张源图属于"可能唯一"，已全部保留。

## 启动不了 / 点了没反应？先看这里

**症状一：双击 `启动机魂修图台.bat` 没反应，或窗口一闪、报 `'xx' is not recognized as an internal or external command`。**

原因是我最初写这个脚本时只写了 **LF 换行**。`.bat` 必须是 **CRLF** 换行 ——
cmd.exe 用纯 LF 解析时，中文行与 `if (...)` 复合语句会被切错，于是报出莫名其妙的"不是内部或外部命令"。
已修复（做了对照实验：同一份内容 LF 版报错、CRLF 版正常）。
脚本同时改用 `goto` 组织流程，彻底避开括号块的解析陷阱。

> 若您日后自己编辑这个 bat，请存成 **CRLF**（Windows 上的记事本 / VS Code 默认就是）。

**症状二：点右上角「退出」没反应。**（v1.4.1 修复）

两个原因，都已修复：

- 我原先用浏览器**原生 `confirm()`** 做确认。浏览器在连续弹窗后会提示"阻止此页面创建更多对话框"，
  一旦勾选，`confirm()` 就**静默返回 `false`** —— 依赖它的按钮于是"点了没反应"。
  同样受影响的还有删除图层、一键抠图、恢复预设。
- `api()` 里 `await fetch(...)` **没有捕获异常**：服务正在退出、连接被重置时，
  异常会让"点完之后的反馈"整个被跳过，页面看起来毫无变化。

现在：**不再使用任何浏览器原生弹窗**（改用应用内确认框）、**点击后立即给出反馈**
（先显示"正在退出…"再发请求）、`api()` 在连不上时返回可读信息；后端改为**优雅退出**
（uvicorn `should_exit`），不再与响应抢跑；`/web/*` 加了禁缓存头，避免浏览器拿旧 JS 造成同类"幽灵问题"。

这条缺陷是靠一个**驱动真实浏览器的回路**钉住的（`tools/check_quit_ui.mjs`，headless Edge + CDP）：
它先安装一个 `confirm` 间谍（返回 false，模拟被阻止），再真的点击「退出」，断言界面必须有可见反应。
修复前是红的（无反应、间谍被调用 1 次、`/api/shutdown` 请求 0 次），修复后 6 项全绿。

**症状三：窗口里出现 `WinError 10048 通常每个套接字地址只允许使用一次`；症状四：指定了 `--port` 却被换到别的端口。**

两层原因，都已修复：

- 旧版 `pick_port()` 用 `bind` 试探端口是否空闲，而 **Windows 上设了 `SO_REUSEADDR` 的 socket
  即使端口已被占用也能 bind 成功**（实测确认）——于是它"成功"挑到一个被占用的端口，
  接着 uvicorn 才报 10048。现在改用 `connect_ex` 判断是否已有服务在听，再用 `SO_EXCLUSIVEADDRUSE` 二次确认。
- 自动模式（不带 `--port`）下端口被占用会自动换端口并打印新地址；
  **但显式 `--port` 时不再静默换端口** —— 悄悄跑到别的端口会掩盖问题（曾经让指向 8760 的检查脚本
  连不上，却不知道服务其实在 8761）。现在会明确报错、退出码 1，并给出换端口的命令。

**症状五：教学模式报「返回 json 格式不对」。**（v1.4.3 修复）

这是本项目里最容易出问题的一处 —— 教学模式一次要输出 summary + 7 项评分 + 优点 + 问题 + 建议，
是最长的结构化回答。实机体检出**七种**真实会挂的输出形态：

| 形态 | 为什么以前会挂 |
| --- | --- |
| JSON 后面跟着一段含花括号的后记（"（未评项用 `{}` 表示）"） | 旧解析器用 `rfind("}")` 取结尾，切到了后记里的括号 |
| 字符串内容里本身就含 `}` | 同上 |
| `//` 注释、尾随逗号、单引号、未加引号的键、中文全角引号与冒号 | 直接 `json.loads` 失败，也不做修复 |
| 回答被 `max_tokens` 截断 | 旧实现甚至从里面抠出一个数组，于是报出"结构不对"这种误导信息 |

现在：**按括号配对取片段**（正确处理字符串与转义，取代 `rfind`）、**自动规整**注释/尾随逗号/单引号/
全角标点/未加引号的键、**截断则补齐结尾**（保住已经完整写好的字段）；若仍不可解析，
会**自动重问一次**"只输出合法 JSON"（截断时同时要求压缩篇幅）；上限也从 4096 提到 6144。

**最重要的是不再含糊**：错误信息会明确指出是"被长度上限截断"还是"没返回 JSON"，
并附上原始返回的末尾片段；界面在总评下方如实标注"已重问一次""采用了截断后的可用部分"。
这些形态全部写成了断言（`tools/check_json_tolerance.py` 17 项 + `selftest_agent.py` 里的教学段 10 项）。

**症状六：裁切之后导出，两边留下白边。**（v1.4.4 修复）

`crop` / `crop_ratio` / `straighten` 是**图层级**操作，只裁图层栅格，不动作画布；而导出画幅由画布决定。
于是 1200×900 做 1:1 裁切后，导出仍是 1200×900，左右各一条白边（实测边缘亮度 1.0）。

现在：**单图层且您未手动定过画布**时，裁切后会自动把画布适配到内容（与整批共用同一个快照，
所以一次撤销能把"裁切 + 适配"一起回退）；一旦您手动改过画布，就标记为 `locked` 不再自作主张；
多图层合成时也不自动改（避免破坏您的合成意图）。

界面按钮同时改名消歧——原先那个「适配画幅」发的其实是 `fit_layer`（把图层缩去适配画布），
方向正好相反，很容易误判：

| 按钮 | 实际动作 |
| --- | --- |
| 图层适配画布 | `fit_layer mode=fit`：图层缩放成刚好装进画布 |
| 图层铺满画布 | `fit_layer mode=fill`：图层缩放成铺满画布 |
| **画布适配内容** | `canvas mode=fit`：**画布缩到刚好包住内容**（裁切后去白边就用它） |
| 画布改 1:1 | `canvas_ratio 1:1`：只改画幅，内容不动 |

**其它可能原因**（脚本现在都会明确提示，不再沉默失败）：

| 窗口提示 | 处理 |
| --- | --- |
| `没有找到 Python` | 安装 Python 3.10+，安装时勾选 `Add Python to PATH` |
| `Python 版本太旧` | 需要 3.10 或更高 |
| `当前 Python 缺少运行依赖` | 按提示执行 `python -m pip install -r requirements.txt` |
| `这个启动脚本必须和 cogitator 文件夹放在同一层` | 把 bat 移回项目根目录（不要单独拷出去） |
| `无法绑定指定端口` | 换一个端口，或去掉 `--port` 让程序自动挑 |

这些都已写成回归断言：`selftest_ops.py` 的「端口探测与启动脚本」一节会真的占住一个端口、
验证 `pick_port` 跳过它，并校验 bat 确实是 CRLF 且无裸 LF；`selftest_shutdown.py` 则覆盖退出链路。

## 设计取舍（最重要的一节）

AI 修图常见的做法是把原图丢给扩散模型重绘。那样"改哪里"无法精确控制，细节会被抹掉。

本项目的做法相反：

**AI 只产出结构化的编辑指令（JSON），像素改动全部由本机确定性算子完成。**

```
自然语言 ──► 模型（DeepSeek）──► {"op":"exposure","value":0.3} ──► 本机 numpy/PIL 算子 ──► 成品
                    ▲                                                      │
                    └──────────── 预览图 + 当前工程状态（可回看反馈）◄──────┘
```

由此得到三个结构性保证，而不是"尽量做到"：

1. **不漂移**：模型碰不到像素。原图字节从不被改写，所有效果都是算子管线，可随时重放。
2. **可撤销**：每批指令前拍快照，整批可撤销；每一步还能单独删除或拖滑杆改参数。
3. **不会瞎编**：《算子手册》由算子注册表自动生成 —— 模型看到的可用动作，就是本机真正会执行的动作。
   模型编出一个不存在操作时，校验器直接拒绝并把错误回灌让它自己改（最多 2 轮）。

## 美商是怎么注入的（v1.1 新增）

「让模型更有审美」不靠换更大的模型，而靠三件事：**给它领域知识、把审美固化成可复现的配方、
用提示词纪律逼它先诊断后动手**。

### 一、技能包（领域知识，渐进式披露）

```
skills/aesthetics/SKILL.md          常驻准则（约 1.4KB，每轮注入）
skills/aesthetics/references/*.md   11 份大部头参考（按需加载）
```

常驻准则里有：**三个必问**（想说什么／眼睛先落哪／删掉什么更干净）、**五条铁律**
（先校正后分级、全局滑杆最后用、幅度最小有效、肤色是红线、质感优先于锐度）、
**看图诊断九步顺序**、**发布前自检六问**、**幅度纪律表**。

11 份参考：构图与视觉重量／色彩与白平衡／用光与光比／人像修图／风光与建筑／静物与美食／
街拍与纪实／风格配方用法／修图工序／常见失误与反例／看图诊断清单。

**关键设计是渐进式披露**：每轮只注入「常驻准则 + 参考索引（标题 + 一句话）」，
模型若判断需要细节，就在返回的 JSON 里写 `"load": ["composition","color"]`，
本机取出正文注入后**重问一轮**。所以提示词永远不膨胀（实测常驻部分约 2KB），
而模型仍拿得到它真正需要的那份知识。这一点由自检实证：断言"第二轮请求里含参考正文，
而第一轮不含"。

### 二、风格配方（把审美固化成确定性算子）

`cogitator/styles.json` 里 13 套配方，每套 = **意图 + 一串已登记算子**：
日系空气感／胶片暖调／电影青橙／暗调氛围／夜景霓虹／奶油人像／通透风光／建筑冷峻／
美食暖香／莫兰迪低饱和／复古褪色／黑白硬调／黑白柔调。

- 套用后**每个算子都独立出现在图层管线里** → 可单独微调、可单独删除、可整批撤销；
- `strength` 0~150 只缩放"强度类"参数，色相角度/比例/形状参数不缩放（否则强度一改方向就变了）；
  强度 0 = 真正的零改动；
- 全部配方逐条过算子注册表校验 —— **写错参数名或超范围会立刻让自检变红**，不可能出现"配方里有本机不支持的操作"。

### 三、提示词纪律：先诊断，再动手，后自检

模型每轮必须产出：`diagnosis`（含具体位置的诊断）→ `intent`（审美意图）→ `ops`（处方）→ 自检。
空话与无依据的改动会被这份结构约束住。

### 四、自动精修（复核轮）

应用指令后，把**执行后的成图**再交给模型复核一遍（可关）：判断意图是否达成、
逐项排查过饱和/过锐化光晕/死黑死白/色阶断层/肤色偏橙/抠图色边，
**允许用 `remove_op` 回退自己刚才的步骤**并给出至多 3 条修正。
复核提示里同样带着"发布前自检六问"，所以这一轮是拿准则在挑自己的错。

### 五、为此新增的算子（48 个）

全局饱和是最容易毁图的动作，专业修图的常规手法是分区与分级，因此补了 4 个算子：

| 算子 | 作用 |
| --- | --- |
| `hsl` | 分区 HSL：只动指定色相带（改绿植、改天空、统一肤色），替代无脑拉全局饱和度 |
| `split_tone` | 分离色调：高光暖 + 阴影冷（电影感/胶片感的核心手法），零均值色偏保持亮度 |
| `vignette` | 暗角收拢视线；正值压暗四角、负值提亮（白晕影通常显廉价） |
| `grain` | 胶片颗粒：中间调最明显、高光暗部收敛，固定种子保证同一文档渲染结果稳定 |

外加 `apply_style`（套用配方，展开为一串独立步骤）。

## RAW（CR3）支持 —— 零依赖拿到全分辨率（v1.2 新增）

相机直出的是 RAW，之前的白名单里没有它。实测本机 **EOS 200D II 的 CR3 里内嵌着一张
6000×4000 的完整 JPEG**（2.4 MB，另有 1620×1080 中等预览与 160×120 缩略图），
而本机既没装 rawpy 也没有 Windows RAW 影像扩展 —— 于是**不需要任何新依赖**就能拿到完整像素。

做法（`cogitator/raw_io.py`）：

1. 遍历文件的 ISO-BMFF 盒结构，扫描 SOI…EOI 得到所有内嵌 JPEG；
2. 用 PIL 逐个**真正解码验证**，挑出像素最多的那张（假 JPEG、小缩略图都会被淘汰）；
3. 落盘时**直接写出文件里的原始 JPEG 字节**——零重编码、零质量损失（自检断言逐字节一致）；
4. 素材里如实记录：来源类型、实际解码方式、原始 CR3 路径、"相机已渲染 8bit"这一局限。

支持 18 种 RAW 扩展名（CR3/CR2/CRW/NEF/NRW/ARW/SRF/SR2/RAF/RW2/ORF/PEF/DNG/RAW/RWL/3FR/IIQ/X3F）。

**诚实标注的两点**：

- 走内嵌预览拿到的是**相机自己渲染的 8bit JPEG**（已套用 Picture Style、已经过影调映射），
  所以没有 RAW 的高光宽容度。这对"调色、修图"够用，对"救回过曝两档"不够。
- 装上 `rawpy` 后本模块**自动改走真正的 RAW 解码**（16bit、相机白平衡、可救高光），
  无需改任何配置；设置页可选择 `auto / 强制 rawpy / 只用预览`。
  **本机未安装 rawpy，因此这条分支只保证同签名同语义，未经实测**（代码里也照实注明了）。

另外修掉了一个容易被忽略的隐患：**PIL 不会自动应用 EXIF 方向标记**，手机/相机竖拍照片
（标记 6/8）会在预览与导出里躺倒。现在导入与渲染两侧都做 `exif_transpose`，
且尺寸按**摆正后**记录，保证几何一致。本机 228 张 CR3 实测标记全为 1（没触发），
但用合成的标记 6 照片做了断言：摆正结果与"顺时针转 90°"逐像素一致、白块落在右上、工程画布随之变成竖幅。

实测数据（E 盘 228 张 CR3，6000×4000）：

| 环节 | 耗时 |
| --- | --- |
| 导入（取内嵌 JPEG + 建工程 + 出预览） | 0.5 s |
| 套用一套 13 步风格（预览渲染） | 1.1 s |
| 按 2400px 导出 | 3.7 s |
| 4 张全流程批量 | 23 s（优化前 177 s） |

## 性能：为什么预览不按 24MP 渲染（v1.2 修复）

拿真实 CR3 测试的第一批结果很难看：**每次改动要 31 秒**，滑杆每拖一次等 31 秒 —— 不可用。

先测量再优化（`tools/profile_ops.py`，24MP 逐算子计时），瓶颈是：

| 算子 | 优化前 | 原因 | 优化后 |
| --- | --- | --- | --- |
| `hsl` | 7630 ms | HSV→RGB 堆了 6 段数组（≈1.7 GB 分配） | 4200 ms → 预览下 ~350 ms |
| `clarity` | 4020 ms | 24MP 上 sigma=22 的高斯 | 225 ms |
| `vibrance` | 1994 ms | 临时数组过多 | 1850 ms →（同类下采样后可控） |
| `contrast` | 163 ms | 每次新建数组 | 74 ms |
| `cv2 高斯 sigma=12` | 1064 ms | 全分辨率大核 | 54 ms |

两处根因修复：

1. **大半径高斯先降采样再模糊再升采样**（模糊本就是低频操作）——sigma=12 从 1064 ms 降到 54 ms。
2. **HSV→RGB 改用 4 个候选值查表装配**，不再堆 6 段；`hsl` 只在**落入该色带**的像素上做往返。

更关键的是架构修正：**预览不按文档全分辨率渲染**。预览按显示尺寸（最长边 1400）渲染，
并以同一比例换算所有"以像素为单位"的参数（裁切坐标、锐化半径、颗粒尺寸、降噪核、蒙版羽化），
得到的正是**「全分辨率导出缩小到该尺寸观看」的效果** —— 与 PS 的 fit-to-screen 预览同理。
导出若指定了尺寸上限，也直接按目标尺寸渲染，而不是"全分辨率渲染再缩小"。

这个加速**不是靠牺牲正确性换来的**：自检里有一条等价性断言 —— 全分辨率渲染后缩到预览尺寸
与直接按预览尺寸渲染，平均差异 **0.0115**、99 分位 0.043、四象限均 ~0.01（属点算子非线性的残差）。
另外还断言了**零算子管线与源图逐像素完全一致**（差异 0.00000；若被旋转/翻转会是 0.39 量级）。

## 推广到其它机器：RAW 解码怎么选（v1.4）

### 结论先行

**首选 rawpy，WIC 作为 Windows 上的免安装回退，内嵌预览作为永远可用的保底。** 三者按此顺序自动回退，
所以任何机器上都至少有一条能用；`auto` 模式不需要用户理解这些细节。

### 为什么不建议二选一（都有实测数字）

| 维度 | rawpy（LibRaw） | Windows RAW 影像扩展（WIC） |
| --- | --- | --- |
| 安装门槛 | `pip install rawpy`：**Windows x64 wheel 仅 921 KB**，PyPI 实测覆盖 cp39–cp314；可**离线打包**（`pip install --no-index --find-links=wheels rawpy`） | Python 侧零安装，但每台机器的用户要自己去商店装扩展；受管/离线机器可能装不了 |
| 平台范围 | Windows / Linux / macOS 全有 wheel（全平台 wheel 合计约 54 MB） | **仅 Windows** |
| 画质与控制 | 可出 **16bit**；白平衡、去马赛克算法、gamma、半尺寸解码都可指定 | **仅 8bit**；编解码器默认渲染，**无参数可控** |
| 每张代价（本机实测） | 进程内、无临时文件（本机未装故未实测耗时） | 整链 **1.47 s**：解码 0.95 s + 进程启动 + **69 MB 临时文件往返** |
| 228 张批量 | 未实测 | 约 **5.6 分钟**；内嵌预览约 **0.8 分钟**（0.22 s/张，无临时文件） |
| 高光宽容度 | 最好（16bit 线性输出可自行处理） | 比内嵌 JPEG 好约 **30 倍**（方差 0.00244 vs 0.00008），但整体更暗（亮度 0.403 vs 0.558） |
| 行为稳定性 | 版本写在 requirements 里，可钉死 | 随 Microsoft Store 更新，**同一文件在不同机器可能得到略不同的源图** |
| 许可 | LibRaw 为 LGPL-2.1 / CDDL 双许可，打包分发需注意动态链接与声明义务 | 系统组件，不引入此类义务 |

### 最关键的一点：解码只影响"导入那一刻"

本项目在导入 RAW 时会**把解码结果物化成工程源图**（`projects/<工程>/sources/A1.jpg`），
因此：

- 同一个工程文件在**任何机器上渲染完全一致** —— 选哪条解码路径都不会破坏跨机一致性；
- 解码路径只决定"**新导入**的照片拿到什么像素"。

这大大降低了选型风险：即使某台机器只有内嵌预览可用，用它导入的照片在本机修完后，
工程拿到别处打开、渲染、导出，结果依然逐像素相同。有断言钉住这一点：
「零算子管线与**工程自己的源图**逐像素一致（差异 0.00000）」——注意基准取的是工程源图，
而不是内嵌 JPEG，否则一旦 `auto` 选了 WIC，这条断言就变成在比较两条解码路径，失去意义。

### 落地：有序回退链 + 每台机器自检

设置里 `raw.decode` 可选 `auto | rawpy | wic | preview`；`auto` 的解析顺序是
**rawpy → WIC → 内嵌预览**。界面「设置 → RAW」会直接列出**本机将走哪条路径**，
以及三条路径各自的可用性与代价：

```
本机将使用：wic（模式 auto）　支持 18 种 RAW 格式
路径                          画质                              代价
✔ rawpy / LibRaw              16bit 可选，白平衡/去马赛克可控    进程内，无临时文件
✔ Windows RAW 影像扩展（WIC）  8bit，编解码器默认渲染            约 1.5 秒/张，约 70 MB 临时文件
✔ 文件内嵌 JPEG 预览           8bit，相机已渲染                  约 0.2 秒/张，零依赖
```

排障也可以直接问接口：`GET /api/raw/status` 返回 `auto_will_use` 与每条路径的 `note`
（写清为什么不可用，例如"未安装 Raw Image Extension"）。

### 分发清单

| 目标机器 | 需要做什么 | 拿到的画质 |
| --- | --- | --- |
| 任意（最低要求） | 什么都不用做 | 内嵌预览：全分辨率（本机 CR3 为 6000×4000），8bit 相机渲染 |
| Windows + 装了 RAW 影像扩展 | 商店装「Raw Image Extension」（免费） | 真 RAW 解码 6024×4020，8bit，高光层次更好 |
| 任意平台 + 可装依赖（**推荐**） | `pip install rawpy`（Windows 上 0.9 MB；可离线打包 wheel） | 真 RAW 解码，可选 16bit，参数完全可控 |

## 原图对比（v1.3 新增，v1.4.2 精简）

修完必须能跟原图对照，否则无从判断得失。两种模式 + 一键导出：

| 模式 | 操作 | 适合 |
| --- | --- | --- |
| **按住看原图** | 按住「按住看原图」按钮、在图上按住，或按住 `\` 键；松开即回成品 | 快速反复确认某一处细节 |
| **擦除** | 点「擦除」后，在图上左右拖动分割线 | 一眼看清哪块变了、变了多少 |
| **导出对比图** | 点「导出对比图」 | 存证/分享：横向并列「原图 \| 成品」并附修改步骤清单 |

> 「按住」是**瞬时**控件：无论当前处于哪种模式，按下立刻显示原图、松开立刻回成品。
> 早先的版本要求先点一下切换模式才生效，于是"第一次按住没反应"——已修（v1.4.2）。
> 早先还有一个「闪烁」模式，按您的要求已移除。

### 一个容易踩的坑：拖图看原图会把成品叠上去（v1.4.2 修复）

`<img>` 默认可拖拽，而 Chrome 在页面内拖动图片时会**把该图塞进 `dataTransfer.files`**。
原先的 drop 处理器只按 `image/*` 过滤、照单全收，于是"在擦除模式下横向拖动分割线"这个动作
会把拖到的预览图当成新素材叠加到画布上（拖到左半区时抓到的是下面的"原图"那张。

现在的三重防护：
1. 两张图都标 `draggable="false"`，并用 `-webkit-user-drag:none` 关掉原生拖拽；
2. 擦除拖动时 `preventDefault()`，并阻止 `dragstart`；
3. drop 处理器只接受**来自系统**的文件（`types` 含 `Files` 且不含 `text/html`/`text/uri-list`），
   页面内拖拽另有标记互相兜底。

这条有真实浏览器断言钉住：擦除模式下用真实鼠标事件横向拖动后，
**图层数、素材数与素材集合都必须完全不变**（修复前是 1→2）。

### 关键设计：对比基准不是"磁盘上的源图"

一旦做过裁切、旋转或校正，源图与成品**画幅不同**，两张叠在一起擦除就对不齐了。
所以本工具的对比基准是**只保留几何算子（裁切/旋转/校正/翻转/缩放）、丢掉调色与蒙版**的渲染结果，
即「同一取景下的未调色版本」——这样才能逐像素对齐地比较。

这一点有断言钉住：
- 未编辑时，基准与成品**完全一致**；
- 只做几何修改时，两者差异 **0.0000**（几何确实保留在基准里）；
- 加 `grayscale` 后，基准仍是彩色（通道差 0.041）而成品已是黑白（0.0000）——证明基准没被成品影响；
- 基准与成品在预览缩放与全分辨率下**尺寸始终一致**（否则擦除模式会错位）。

界面上「对比原图」控件只在**存在调色类修改**时才出现（用 `state.edited` 判断）；
支持深链 `?cmp=wipe|hold` 直接进入某个模式。

- **套风格**：「图层」标签页顶部的风格配方栏 —— 选配方、拖强度（默认 80%）、点「套用」。

- **微调**：在「图层」里点任意一步（如 `exposure value=0.3`），底部出现滑杆，拖动即时生效；
  点该步右侧 `✕` 可单独删掉这一步。
- **一键抠图**：图层卡片上的「一键抠图」（首次约 6 秒装载模型，之后单张约 1 秒）。
- **教学模式**：顶部「教学模式」→「教学」页给出分项评分与拍摄建议，可一键应用它给的修图。
- **知识库**：「设置 → 审美技能包」可浏览 11 份参考正文；直接编辑 `skills/` 下的 md 文件后
  点「重新加载技能包与配方」即可生效（无需重启）。
- **网络**：「设置 → 网络」可启用本机代理（默认 `http://127.0.0.1:7897`）并一键检测
  DeepSeek / HuggingFace / OpenAI 的直连与代理可达性。
- **导出**：顶部「导出」，可选格式/质量/最长边/另存路径；PNG 保留透明，JPG/WEBP 自动压白底。

**算子注册表是唯一契约来源**（`ops.py` 里的 `SPECS`）。同一份定义同时负责三件事：

1. 校验模型产出的指令（类型、范围、枚举、必填/可选）；
2. 生成给模型看的《算子手册》；
3. 索引实现函数（管线算子 → `image_ops`，蒙版算子 → `document` 物化，结构算子 → `document`）。

自检里有一条硬断言：**每个登记算子必须有实现，且不能有游离实现**。所以"模型说的"和"本机做的"无法漂移。

两条不变量贯穿全码：

- **源图永不被改写**，效果全部是可重放的管线；
- **一批指令要么全部落地，要么一条都不落地**（校验先于执行，执行中途异常则回滚快照）。

## 已知限制（如实列出）

1. **抠图完全离线，不依赖联网**：复用本机权重 `C:\AI\ComfyUI\models\RMBG\RMBG-2.0`。
   （首轮开发时实测 HuggingFace 直连超时；开启本机代理后已可达 —— 实测 `HTTP 200 / 0.3s`。
   但抠图仍走离线装载，因为这样更快也更可靠；换机器时请在设置里指向自己的 BiRefNet/RMBG 权重目录。）
2. **代理仅用于模型接口**：`httpx >= 0.28` 的关键字是 `proxy=`（单数），旧写法 `proxies=` 会直接 TypeError；
   本机默认不走代理（直连即可用），需要时在「设置 → 网络」启用并点「检测网络」核对。
3. **BiRefNet 走 fp32**：实测 fp16 会因部分子模块未随之转换而报错
   （`Input type (Half) and bias type (float)`），而 fp32 单张不到 1 秒，够用，因此没有做半精度优化。
4. **GrabCut 兜底精度有限**：适合主体与背景对比明显的图，发丝/透明边缘不如 BiRefNet，只作为权重缺失时的退路。
5. **教学模式按你的选择只依据视觉模型读图**：没有配置支持读图的模型时，它会明确报错并让你换模型，
   不会用本机指标假装看过照片。
6. **单用户单进程**：对话与编辑走同一把进程内锁，同一时刻只处理一个请求；这是本地单人工具的取舍，不是并发服务。
7. **自动精修会多花一轮调用**：默认开启，可在对话栏或设置里关掉（关掉后每轮只调用一次模型）。
8. **多轮对话只带文本历史**：为避免 token 爆炸，历史消息不重复附图，只有当前这一轮带最新预览图
   （DeepSeek 也要求图片只能出现在 user 消息里）。
9. **JSON 输出偶发为空**：DeepSeek 官方文档说明 JSON Output 有概率返回空 content，
   本工具会重试（最多 2 次）并把校验错误回灌给模型。
10. **风格配方不缩放形状参数**：`feather`（过渡柔和度）/`size`（颗粒尺寸）/`radius`/`width` 不随强度变化，
    否则强度一改就把过渡与颗粒也压没了；`strength=0` 表示完全不改动。
11. **`remove_op` 按序号删除**：序号是操作在该图层管线里的下标（从 0 计，−1 表示最后一步）；
    删掉中间一步后，其后步骤序号会前移。`delete_layer` 是唯一必须写明目标图层的算子（破坏性操作）。
12. **技能包改动需点一次重新加载**：编辑 `skills/` 下的 md 后，在设置页点「重新加载技能包与配方」即可生效，
    无需重启服务。
13. **RAW 走内嵌预览时没有 RAW 宽容度**：拿到的是相机已渲染的 8bit JPEG（高光已定死）。
    要真正的 16bit RAW 解码需 `pip install rawpy`，装上后本工具自动改走该路径；
    但**该分支在本机未实测**（本机未安装 rawpy），代码里已如实标注。
14. **锐化/颗粒在预览与导出尺寸下观感不同**：预览按显示尺寸渲染（与 PS 的 fit-to-screen 同理），
    1px 锐化在 1400px 预览里几乎不可见、在 6000px 导出里才显现 —— 这是分像素处理的固有性质。
    判断锐化程度请以导出后的实际查看尺寸为准；本工具暂不提供 100% 放大视图。
15. 顶部「退出」按钮会直接关掉本地服务进程（工程已自动保存）；重新使用就再双击一次 `.bat`。
